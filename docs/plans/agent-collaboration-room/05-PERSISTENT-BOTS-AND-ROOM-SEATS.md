# 持久 Bot 与智能体会话：身份、上下文与协作运行时

> 状态：讨论稿，已记录 2026-08-20 已确认产品模型；其余细节待决  
> 日期：2026-08-20  
> 上位文档：[协作室总纲](./00-MASTER.md) · [Runtime / A2A 规格](./02-RUNTIME-A2A-SPEC.md) · [Hermes 机制移植规格](./04-HERMES-BORROW-SPEC.md) · [ADR-0006](../../decisions/ADR-0006-role-vs-soul.md) · [ADR-0007](../../decisions/ADR-0007-agent-collaboration-room.md)

## 0. 一句话

把用户配置过、可长期复用的 Agent 定义为 **Bot**；把 Bot 加入某个协作室后的房间内实体定义为 **席位（RoomMember / Room Seat）**。

> Bot 是长期存在的源身份；席位是 Bot 在某个房间里的派驻实例；Run 是席位的一次临时执行。

Bot 不是一个永不结束的 KSCC session。KSCC session / 进程只是某个具体上下文的执行载体，允许长驻、压缩、替换和恢复。

## 1. 要解决的问题

当前角色库表达的是岗位契约；协作室表达的是房间、成员、消息、mailbox 和 run。二者之间缺少一个可被用户长期配置、反复调用、可加入多个协作室的“数字员工”实体。

仅靠“角色卡 + 模型 + 渠道”的组合，用户得到的是一个预设，不是可被称呼、可积累记忆、可被派驻和可被唤醒的 Bot。

同时，若把一个 Bot 直接等同于唯一的永久会话，会带来以下错误：

- 多个房间和普通会话互相污染上下文；
- 同一 Bot 不能安全并行参与多个房间；
- 房间的私有信息可能被带到其他房间；
- 修改 Bot 配置会无声改变正在进行或已完成房间的行为解释；
- KSCC 的压缩、崩溃恢复或 session 替换会影响所有业务场景。

本设计通过“Bot 源身份 + 房间席位 + 场景会话 + Run”分层解决这些问题。

## 2. 概念与关系

```text
BotProfile（长期、全局、可复用）
  ├─ 普通会话临时咨询 ──> AgentSession ──> Run
  ├─ 与用户的专属 Bot Chat ──> AgentSession ──> Run
  ├─ 协作室 A ──> RoomMember（席位 A） ──> AgentSession ──> Run
  ├─ 协作室 B ──> RoomMember（席位 B） ──> AgentSession ──> Run
  └─ cron / mailbox / 外部事件 ──> AgentSession ──> Run
```

| 实体 | 生命周期 | 负责什么 | 不负责什么 |
| --- | --- | --- | --- |
| `BotProfile` | 用户主动创建、暂停、归档、删除 | 名称、身份、默认模型/渠道、工具、权限、长期记忆命名空间 | 房间历史、单次运行状态 |
| `RoomMember` | 随房间加入/移除，可保留历史 | Bot 配置快照、房间职责、房间权限、房间会话绑定 | 修改 Bot 本体、跨房间共享房间记忆 |
| `AgentSession` | 某个场景中的连续对话 | 该场景的逻辑上下文、resume 指针、压缩链 | Bot 的全局身份或其他场景上下文 |
| `Run` | 一次唤醒到终态 | 排队、执行、工具过程、取消、产物和审计 | 持久人格或长期记忆 |
| KSCC 进程 / `sdkSessionId` | 运行期实现细节 | 当前 session 的高性能执行、resume、压缩/重建 | 业务真值、Bot 身份 |

### 2.1 Bot 不是角色卡的同义词

产品界面可以把原先的“角色库”升级为 **Bot 库** 或 **Agent 库**：用户看到的是可配置、可直接使用的 Bot。

内部仍保留角色的价值：角色是 Bot 的岗位能力来源或初始模板；Bot 是用户拥有的、带状态和长期身份的实体。这样不会把“研究员”这一可复用岗位模板和“我的研究助手小李”这一可持续配置的 Bot 混成同一对象。

### 2.2 席位不是“假 Bot”或完全克隆

用户语言应是：

> 将“研究助手”派驻到此协作室。

而不是“复制一个 Bot”。席位是对同一 Bot 的一个房间绑定：它继承当时的 Bot 配置，但把房间职责、权限、会话和记忆隔离在本房间中。

成员卡需要清楚显示：

```text
研究助手
来源：研究助手 Bot · 配置 v3
房间记忆：仅此协作室
[更新到最新 Bot 配置]
```

## 3. 配置快照与更新规则

### 3.1 加入房间时

将 Bot 加入房间会创建一个 `RoomMember`，至少记录：

```ts
interface RoomMember {
  id: string
  roomId: string
  botId: string
  sourceBotRevision: number
  botSnapshot: BotRuntimeSnapshot
  roomRoleOverride?: string
  roomPermissionOverride?: PermissionProfile
  logicalSessionId: string
  backendResumeToken?: string
  status: MemberStatus
}
```

`botSnapshot` 是可执行行为的快照：身份/SOUL、模型与渠道默认值、工具集、权限、能力开关等。它使房间的历史、审计和恢复拥有稳定解释。

### 3.2 修改 Bot 后

修改 Bot 本体会生成新 revision，但不会静默修改已有席位。

- 新建普通调用和新加入的房间席位默认使用最新 revision；
- 已在房间内的席位继续使用加入时的 snapshot；
- 用户可在成员详情中显式“更新到最新 Bot 配置”；
- 更新是一次可审计的席位变更，而不是覆盖历史。

### 3.3 移除、归档与删除

- 从房间移除席位不会删除 Bot；
- 归档 Bot 后，既有历史保留，但不再接受新的自动唤醒；
- 删除 Bot 前必须说明受影响的房间席位；已发生的消息、run 与 snapshot 需要保留为可审计历史，不应失去作者归因；
- 已删除/归档 Bot 的历史席位显示“已归档的 Bot”，而非回退成无名角色。

## 4. 上下文与记忆边界

### 4.1 四层上下文

每次调用不读取“Bot 的全部历史”，而由宿主按场景装配：

```text
1. Bot 身份层
   SOUL、稳定工作方式、默认能力、不可变安全边界

2. Bot 长期记忆层
   经筛选的偏好、可泛化专业经验、用户允许持久化的事实

3. 场景层
   普通会话历史，或协作室目标/共享摘要/成员可见消息/mailbox/任务

4. Run 层
   本次触发、工具过程、临时文件、审批与短暂中间状态
```

在协作室中，`RoomMember` 看到的是房间场景层，而不是 Bot 其他房间的完整 transcript。成员自己的历史发言投影为 `assistant`，其他参与者的发言投影为带归因的 `user`；这一原则沿用现有协作室上下文投影设计。

### 4.2 记忆读写规则

| 数据 | 归属 | 默认可见性 | 写入策略 |
| --- | --- | --- | --- |
| Bot 身份与长期记忆 | `bot:<botId>` | 由 Bot 的授权范围决定 | 受控记忆工具或用户确认；保存 provenance 和范围 |
| 房间共享摘要 | `room:<roomId>` | 房间参与者 | 独立总结器生成；不自动回写 Bot |
| 房间私有 mailbox / A2A 内容 | `room:<roomId>:member:<id>` | 按收件人/协调者规则 | 宿主签发、可审计、按房间清理 |
| 普通会话 transcript | `chat:<sessionId>` | 该会话 | 不自动写入 Bot 长期记忆 |
| Run 工具轨迹 | `run:<runId>` | 详情/审计 | 终态后归档或按策略清理 |

默认原则：**房间发生的内容不自动成为 Bot 的长期记忆。**

若有值得跨场景复用的结论，采用显式晋升：用户点击“保存为 Bot 记忆”，或 Bot 提出结构化保存建议，由宿主校验范围、敏感性和来源后写入。私密房间内容默认不能晋升。

### 4.3 谁管理上下文

Bot 可以通过受控工具建议“记住”“遗忘”“总结”，但不能自行决定原始聊天记录、记忆范围和跨房间可见性。

> Bot 决定哪些信息可能有长期价值；宿主决定是否保存、保存到哪里、谁可见、何时过期。

这避免模型把提示注入、临时任务细节或其他用户/房间的私密信息写入全局记忆。

## 5. KSCC session 语义

KSCC 的“会话=长驻进程”是性能策略，不是 Bot 身份模型。

每个 `AgentSession` 可绑定一个当前 `sdkSessionId`，并在其热期复用 KSCC 进程；但 Bot 在不同房间、普通会话和后台触发中拥有不同的逻辑会话。宿主负责：

- 从 `AgentSession` 恢复或创建当前 KSCC session；
- 在上下文过长时执行已有的压缩/软重置策略；
- 将新的 `sdkSessionId` 写回该场景的 session binding；
- 在空闲、故障、取消或资源紧张时释放进程，而不丢失 Bot、房间或审计真值。

因此，不采用以下模型：

```text
一个 Bot = 一个永久 KSCC session = 所有房间和普通会话共享
```

正确模型是：

```text
一个 Bot = 多个按场景隔离的 AgentSession
一个 AgentSession = 当前可替换的 KSCC sdkSessionId / 进程
```

## 6. 普通会话中的 Bot 调用

普通会话应支持两种不同语义，避免用户误以为每次 `@Bot` 都在修改 Bot 的永久聊天：

| 操作 | 含义 | 默认上下文 | 是否写入 Bot 长期记忆 |
| --- | --- | --- | --- |
| `@研究助手 帮我评估…` | 一次临时咨询 | 当前普通会话的必要投影 + Bot 身份/相关记忆 | 否 |
| “与研究助手继续聊天” | 打开该 Bot 的专属对话 | 专属 Bot Chat 的 session | 仅经受控记忆流程 |
| “加入协作室” | 创建房间席位 | 房间摘要、房间消息、mailbox、任务 | 否，除非显式晋升 |

临时咨询可以产生一个短生命周期 `AgentSession`，也可以在同一普通会话内维持可续接的 Bot 参与者 binding；无论实现如何，它不应与协作室 session 或 Bot 专属聊天共用 transcript。

## 7. 运行与并发

同一个 Bot 可被多个场景同时调用，但并发规则必须显式：

- 每个 `RoomMember` 默认一次只运行一个 turn，保证该房间的因果顺序；
- 不同房间的不同席位可并行；
- Bot 全局可设置并发上限，避免同一凭证、工作区或外部渠道被过度占用；
- 涉及同一工作区写入时，仍由工作区锁/审批策略决定，不能因为它们来自同一 Bot 而绕过隔离；
- A2A handoff 的深度、循环与重试归属房间，而不是归属 Bot 全局。

## 8. 最小持久化模型

首期无需把全部记忆系统重做；先增加可清楚表达归属的实体与引用关系：

```ts
interface BotProfile {
  id: string
  displayName: string
  description: string
  soul: string
  defaultBackend: 'pi' | 'channel' | 'cli'
  defaultChannelId?: string
  defaultModelId?: string
  defaultPermissionProfile: PermissionProfile
  capabilities: MemberCapabilities
  memoryNamespace: string
  revision: number
  status: 'active' | 'paused' | 'archived'
}

interface AgentSessionBinding {
  id: string
  botId: string
  surface: 'bot_chat' | 'chat_consultation' | 'room' | 'routine' | 'mailbox'
  surfaceId: string
  logicalSessionId: string
  backendResumeToken?: string
  activeSdkSessionId?: string
  status: 'idle' | 'running' | 'paused' | 'closed'
}
```

现有 `CollaborationMember` 可演进为 `RoomMember`：保留当前的 `roleSnapshot` / `logicalSessionId` / `backendResumeToken`，新增 `botId`、`sourceBotRevision` 与 `botSnapshot`。迁移时，历史成员可生成“本地/未关联 Bot”的兼容 Bot Profile，不需要篡改历史消息。

## 9. 对 Hermes Agent 与 Hermes Studio 的取舍

本设计不是照搬任何一方：

- **借 Hermes Agent**：Bot/Profile 是长期可复用身份；一个 Bot 可有专属聊天、定时任务、跨场景调用和多个群组上下文。
- **借 Hermes Studio**：房间是独立运行时；成员配置、消息、压缩、队列、handoff 和安全边界有房间级真值。
- **保留 TAgent 边界**：协作室仍是独立 Rail/容器；房间成员不能因“Bot”身份绕过工具白名单、看板真值、预算、审批或工作区权限。

最终方向不是“把协作室做成 Bot Chat”，而是：

> 用长期 Bot 提供可复用身份；用独立协作室提供可审计的团队协同；用场景 session 保护上下文边界。

## 10. 待决策项

1. 用户界面名称：保留“角色库”并增加 Bot 模式，还是升级为“Bot 库 / Agent 库”？
2. Bot 长期记忆的第一期范围：只支持用户显式保存，还是允许低风险专业知识自动提议保存？
3. Bot 配置更新策略：房间席位默认固定快照，还是支持可选“持续跟随最新配置”？
4. 一个 Bot 是否允许绑定多个渠道/模型作为 fallback，还是首期只支持一个默认选择？
5. 普通会话中的临时咨询是否创建可续接的会话 binding，还是每次完全一次性？
6. Bot 归档/删除时，房间席位和历史消息采用何种 retention 与展示策略？
7. Bot 的长期记忆是否区分私有记忆、专业记忆和可共享记忆，并如何与现有记忆层衔接？

在这些问题被明确之前，本文件不修改 ADR-0006 的“角色是岗位契约，不是进程”结论；它提出的是在角色与 run 之间增加 `BotProfile` 这一持久身份层的候选架构。

## 11. 2026-08-20 已确认的产品模型（本节优先）

本节记录后续讨论已确认的产品决策，并优先于本文早期“协作室独立 Rail / 独立用户入口”的表述。这里改变的是产品信息架构；现有协作室的多人运行时、数据模型与审计能力仍是复用基础。

### 11.1 两种用户侧会话模式

用户不需要在“普通会话、Bot 会话、协作室”之间先做分类。产品层只保留两类：

| 用户侧模式 | Bot 数量 | 体验与运行时 |
| --- | ---: | --- |
| 普通会话 | 0 | 复用现有稳定的单 Agent `Session`，由现有主助手承接 |
| 智能体会话 | 1+ | Bot 是对话参与者；1 Bot 仍复用单 Agent `Session`，2+ Bot 才在后台挂接现有 `CollaborationRoom` runtime |

因此，“与研究助手聊天”是 1:1 智能体会话；加入前端搭档后仍是同一类智能体会话，只是成员增加。协作室不再是要求用户跳转进入的独立产品，而是多人智能体会话按需开启的协作能力。

### 11.2 加入 Bot 的默认行为

```text
普通会话
  ├─ @研究助手               -> 一次临时咨询，普通会话不变
  └─ 与研究助手继续协作       -> 创建/继续 1:1 智能体会话

1:1 智能体会话
  └─ 加入第二个 Bot           -> 创建或挂接多人协作 runtime，界面仍为同一套对话壳层
```

- 第一个 Bot 加入后即可直接对话，不要求配置协调者、任务或房间；它与普通会话使用同样稳定的单 Agent 执行路径。
- 加入第二个 Bot 时，不把原单 Agent session 原地改造成多人 runtime；以可编辑摘要、进行中任务和已选产物建立多人上下文，保留原会话以避免稳定性与隐私问题。
- “Bot 专属聊天”不是独立产品对象，而是“有一个指定 Bot 参与的 1:1 对话”。Bot 库只负责发现、配置、开始/继续对话和邀请加入。

### 11.3 多人默认协调与消息路由

多人智能体会话仍需要协调者，但协调者不再证明存在一个独立的“协作室产品”。它是该对话内的协调席位：默认由第一个加入的 Bot 担任，用户可在高级成员设置中转交。

```text
@某个 Bot        -> 指定 Bot
回复某条消息     -> 原消息 Bot 或任务负责人
关联已有任务     -> 任务负责人
未指定成员的消息 -> 当前协调者（默认第一个 Bot）
```

协调者可以直接回答、拆分子任务、委派成员、等待结果后汇总，或向用户澄清；不得因为未 @ 就默认群发给所有 Bot。只有 1 个 Bot 时，该 Bot 直接承接所有消息，不需要协调席位。

### 11.4 用户任务与协作工作层

用户在多人智能体会话中发送任务后，Bot 间协调不应污染主聊天流：

```text
用户发任务
  -> 协调者判断：直接回答 / 需要协作
  -> 创建并分派子任务
  -> 成员 Bot 在各自受限上下文中执行、交接与回报
  -> 协调者汇总面向用户的答复
```

主聊天默认呈现协调者答复和紧凑工作卡；用户按需展开查看分派、交接、产物、审批与运行记录。现有协作室的 scheduler、A2A / mailbox、任务、产物、审批、时间线、摘要和审计能力都应直接复用。

### 11.5 成员替换、移除与协调交接

用户看到的是“更换 Bot / 移除”，底层语义必须是“旧席位退场 + 新席位加入 + 受控交接”，不能把一个 Bot 原地改名成另一个：

| 情况 | 默认处理 |
| --- | --- |
| 更换空闲成员 | 新 Bot 读取交接包：对话摘要、相关任务、产物、待确认事项；不继承旧 Bot 的私有上下文或长期记忆 |
| 移除工作中成员 | 提示“转交给其他 Bot / 等当前工作完成后移除 / 立即停止” |
| 更换或移除协调者 | 先生成协调交接摘要；默认预选第一个剩余 Bot 接任，用户可改选 |
| 剩 1 个 Bot | 自动降为 1:1 智能体会话，不再启用协调、A2A 与多人编排 |
| 移除最后一个 Bot | 不静默切换为默认助手；提供“换一个 Bot / 改为普通会话 / 归档” |

全局归档 Bot 后，禁止新建与新加入，但保留历史归因。永久删除前必须处理活跃席位和运行中任务；历史消息、run 与 snapshot 需显示“已删除 Bot”的可审计快照。

### 11.6 工具能力与现有协作室复用

Bot 不是能力更弱的群聊成员。在同渠道、同模型和同权限配置下，Bot 的基础工具能力必须与普通会话 Agent 相同：文件、终端、浏览器、Skills、MCP、工作区能力及其审批流均复用现有 Agent runtime。

```text
Bot 能力 = 普通会话 Agent 工具能力
         + A2A / 交接
         + 领取和更新任务
         + 读取多人摘要与产物
         + 向协调者回报结果
```

多人协作只叠加协作工具，不替换基础工具。每个成员仍按自身 BotProfile 与席位权限执行；审批显示具体 Bot 与所属任务，多 Bot 写同一工作区继续受任务归属、文件锁、审批和冲突提示约束。

实现上不新造“融合会话 runtime”：

```text
统一对话界面 / 侧栏
  ├─ 0 / 1 Bot -> 现有 Session runtime
  └─ 2+ Bot   -> 现有 CollaborationRoom runtime
```

首期通过统一对话索引和共同页面壳层聚合现有 Session 与 CollaborationRoom；现有协作室的独立 Rail、建房流程和用户术语逐步收敛为“加入 Bot / 成员设置”，不要求立即迁移或重写多人数据。

### 11.7 仍待决策

下一优先级是 Bot 长期工作记忆：哪些信息可自动提出保存建议、在新 1:1 对话 / 多人对话 / `@` 临时咨询中分别读取哪些 scope，以及如何避免跨对话的私密信息泄漏。其余待决项仍包括产品名称、Bot 配置更新、渠道 / 模型 fallback、临时咨询 binding 与永久删除 retention。

### 11.8 统一页面、侧栏与标签页

普通会话与智能体会话使用同一个对话页面、同一个侧栏和同一个标签页系统。创建时不要求用户选择“普通模式 / 融合模式”，而是选择参与者：

```text
新建对话
  参与者：[默认助手] [研究助手 Bot] [前端搭档 Bot] ...
```

参与者数量决定后台能力：

```text
默认助手       -> 普通会话
一个 Bot        -> 1:1 智能体会话
多个 Bot        -> 多人智能体会话，第一个 Bot 默认主理
```

不为三种场景分别实现三套 UI。消息流、输入框、标签页、成员头像与基础会话操作使用同一个对话壳层；多人对话只按需显示任务、协作、产物、审批和审计区域。

标签页表示一段可打开、可恢复、可并行运行的对话，不直接暴露底层 runtime 类型。用户可同时混排普通对话、Bot 1:1 对话和多人 Bot 对话。


普通会话后来加入第二个 Bot 时，底层可以创建带摘要的新多人协作 runtime，但界面保持在统一对话壳层中；原普通会话保留，避免直接修改既有 Session 的稳定性与隐私边界。

### 11.9 Bot 工作笔记：候选与激活分离

Bot 的工作笔记持久化在本地硬盘上，但“写入硬盘”不等于“进入 Prompt”。所有由 AI 整理出的新笔记先进入候选区：用户未确认前，检索器不得将其注入任何 Bot 上下文。

```text
聊天 / Run / 工具结果
  -> AI 整理、去重、精炼、归类
  -> 硬盘上的候选笔记（candidate）
  -> 用户查看 / 编辑 / 确认
  -> 激活笔记（active）
  -> 仅在匹配场景中检索并进入 Prompt
```

AI 可以自动完成摘要、合并重复笔记、补充来源、标记敏感性、建议作用域和生成新版本；但不能把未确认内容作为 Bot 已知事实使用。已激活笔记的后续精炼也应生成可审阅的修订版本，不应静默改变 Bot 的有效记忆。

每条笔记至少需要记录：内容、状态（候选 / 激活 / 拒绝 / 归档）、来源引用、作用域、创建与更新时间、精炼版本和用户确认记录。普通 1:1 Bot 对话可读取相关激活笔记；多人对话只读取允许复用的激活笔记；`@Bot` 临时咨询只读，不写入长期记忆；房间内容默认不会自动晋升。

### 11.10 Bot 配置版本与会话更新

Bot 的行为配置采用不可变版本；Bot 的工作记忆独立动态更新。配置版本包括 SOUL / 系统提示词、默认模型与渠道、工具能力、权限范围和协作能力。

```text
研究助手 Bot
  ├─ v1：旧配置
  ├─ v2：当前配置
  ├─ 对话 A -> 使用 v1
  └─ 对话 B -> 使用 v2
```

- 新建对话默认使用 Bot 最新版本；已有对话继续使用创建时的版本。
- Bot 配置修改后，已有对话显示“Bot 有新版本”，用户显式点击“更新到 v2”后才切换。
- 正在运行的 Run 不被配置更新中断；更新从下一轮开始生效，并记录 `v1 -> v2` 的审计事件。
- 多人智能体会话中，每个 Bot 席位可以单独更新，也可以执行“全部更新”。
- 已确认的工作记忆可以持续增长，不因为每条新记忆而生成新的 Bot 配置版本；每次 Run 记录实际使用的记忆版本。
- 权限收紧（例如撤销终端或写入能力）可以立即生效；权限扩大必须用户显式确认。

用户只需要看到：

```text
研究助手有新配置
[继续使用当前版本] [更新到 v2]
```

### 11.11 多用户融合会话：人类成员与他人 Bot

本节是 2026-08-20 的可行性讨论稿，记录设计假设，不代表已经通过原型、联调或安全测试。最终行为必须以实现验证结果为准。

多人融合会话不能继续把会话理解为“某个用户本地会话里挂了几个 Bot”，而应升级为服务端权威的 `RoomSession`。房间成员包括真实用户和 Bot：

```text
用户 A
  ├─ 研究 Bot
  └─ 编程 Bot

用户 B
  └─ 设计 Bot

RoomSession
  ├─ HumanMember A
  ├─ HumanMember B
  ├─ RoomBotSeat：研究 Bot，所有者 A
  ├─ RoomBotSeat：编程 Bot，所有者 A
  └─ RoomBotSeat：设计 Bot，所有者 B
```

必须区分三个层次：

```text
BotProfile
  Bot 的长期身份、配置、私有记忆和所有者

RoomBotSeat
  Bot 在某个房间中的成员席位、权限、配置快照和运行来源

RoomAgentSession
  Bot 在该房间中的独立上下文、任务和运行状态
```

其他用户的 Bot 加入房间后，不继承其所有者的私聊历史、私有 Bot 记忆、个人工作区或其他房间上下文。它只读取当前房间公开内容、房间允许的任务和明确共享的产物。房间结束后，房间上下文也不应自动写入 Bot 的长期记忆。

Bot 的所有者权限与房间权限相互独立：房间可以邀请一个 Bot，但不能因此取得该 Bot 所有者的私有资源；Bot 所有者也不能因为拥有 Bot，就绕过房间的权限、审批和任务范围。

建议采用以下有效权限交集：

```text
Bot 实际能力
  = Bot 自身权限
  ∩ 房间策略
  ∩ 当前任务范围
  ∩ 资源所有者授权
```

多人房间中的消息路由建议为：

```text
未指定对象的消息 -> 当前房间协调者
@某个 Bot        -> 公开提交给该 Bot，房间成员可见
@某个用户        -> 指定或提醒该用户
@all             -> 全体成员，按房间策略限制使用
```

普通会话中的 `@Bot` 默认打开用户私有的悬浮咨询；多人融合会话中的 `@Bot` 默认表示公开提及。多人房间如果要私下咨询 Bot，应从 Bot 成员菜单选择“私聊 Bot / 打开咨询小窗”。私聊小窗可以读取房间公开投影，但内容不会自动进入房间时间线。

### 11.12 普通会话升级为多人会话

普通会话可以在产品体验上升级为多人融合会话，但不能原地扩大原有私有会话的权限边界。底层应从原会话派生一个新的 `RoomSession`，原普通会话继续保留：

```text
普通私有会话
  ├─ 继续和默认助手聊天 -> 保持原 Session
  ├─ 加入一个 Bot      -> 可继续使用单 Agent Session
  └─ 加入第二个 Bot / 其他用户
       -> 创建新的 RoomSession
          ├─ 复制经过筛选的摘要
          ├─ 用户选择要共享的消息
          ├─ 用户选择要共享的文件
          ├─ 建立 RoomWorkspace
          └─ 建立 HumanMember / RoomBotSeat
```

“升级”时默认不得带入完整私聊历史、个人工作目录、私有 Bot 记忆、未确认笔记或未明确分享的文件。用户可以选择分享当前结论、指定消息或指定文件；原会话和新房间之间保留来源关联，但不共享完整上下文。

### 11.13 多用户房间的本地文件边界

多人房间不是所有用户本地磁盘的并集。Bot 默认不能读取任何成员的本地文件。文件至少区分为：

| 资源类型 | 默认可见范围 |
| --- | --- |
| 用户私有文件 | 文件所有者和被授权的本地 Bot |
| 房间工作区文件 | 房间成员和获得房间权限的 Bot |
| 任务附件 / 共享产物 | 指定任务、指定 Bot 或房间成员 |

第一期建议为多人房间创建独立的 `RoomWorkspace`，而不是直接把某个用户的个人工作目录挂到房间：

```text
用户选择文件 / 文件夹
  -> 分享给房间或指定任务
  -> 创建受 ACL 保护的 RoomArtifact
  -> Bot 通过资源引用读取
  -> 修改结果生成新版本或补丁
  -> 覆盖原文件需要文件所有者或房间策略审批
```

Bot 不应直接获得成员机器上的绝对路径，而应通过受权限控制的资源引用访问，例如 `room://<roomId>/artifact/<artifactId>`。文件的读取、下载、写回、版本和审批均应记录审计事件。

如果房间任务必须操作某个用户电脑上的本地文件，应通过该用户设备上的 Local Worker 执行：

```text
Room Server -> 用户 A 的 Local Worker -> 用户 A 授权
            -> 在限定目录执行 -> 返回产物或补丁
```

其他用户的 Bot 不能直接访问用户 A 的电脑；用户 A 关闭客户端或 Worker 离线时，相关任务应显示离线并排队、暂停或转交。

### 11.14 多用户融合会话的服务端形态

当前 TAgent 的桌面 IPC 适合单用户本地运行，不足以直接承担跨用户房间。多人能力需要一个房间服务端作为唯一真值来源：

```text
用户 A 客户端 ─┐
用户 B 客户端 ─┼─ WebSocket / HTTP -> Room Server
用户 C 客户端 ─┘                       ├─ 账号、邀请码与成员权限
                                        ├─ 房间事件与消息持久化
                                        ├─ 协调者和 Bot Seat 运行
                                        ├─ 任务、审批、产物和审计
                                        └─ 实时广播与重连恢复
```

局域网和广域网是同一套协议的不同部署方式：

- 局域网：一台电脑或内网服务器运行 Room Server，其他设备通过内网加入；适合作为第一期原型和自托管模式。
- 广域网：Room Server 部署到 VPS 或云服务，通过域名、TLS、账号和邀请码访问；需要额外处理公网安全、限流、数据隔离和远程 Worker。
- 混合模式：房间状态和消息在服务端，Bot 或本地文件操作通过用户设备上的 Worker 执行。

首期可优先验证“局域网服务端 + 独立 RoomWorkspace + 显式文件分享 + 多用户 WebSocket 房间”。协议和权限模型应按广域网设计，避免以后重新定义成员、房间事件和文件授权。

### 11.15 必须通过实现验证的假设

以上模型目前仍是架构假设，至少需要通过以下验证后才能作为正式实现结论：

1. 两个以上用户同时加入同一房间，消息顺序、重连和历史恢复正确。
2. 同一房间同时运行多个 Bot，任务路由、协调、取消和审批不串线。
3. 一个用户的 Bot 加入另一个用户创建的房间时，私有记忆、私聊历史和个人文件不会泄漏。
4. 普通会话派生为 `RoomSession` 后，原会话仍保持原有上下文和权限。
5. 文件分享、只读、写回、版本、撤销授权和审计链路能够闭环。
6. Bot 所有者离线、客户端关闭或 Local Worker 断线时，房间状态能明确显示并安全恢复。
7. 局域网连接、账号认证、邀请码和权限拒绝行为通过端到端测试。

在这些验证完成前，文档中的“可行”只表示设计上有清晰的实现路径，不表示已经证明没有并发、隐私或运行时风险。

### 11.16 房间工作区与成员产物下载

房间需要拥有一个实际存在的服务端工作区，作为多人协作产出的唯一真相。局域网自托管时，该工作区通常位于房主或指定内网主机的 Room Server 数据目录；广域网部署时位于云端持久化磁盘、工作区容器或等价的持久化存储中。产品和数据模型不应绑定“房主个人目录”，而应绑定 `RoomServer + roomId`。

```text
Room Server Data/
  rooms/<roomId>/
    workspace/
      shared/
      members/<userId>/
      artifacts/
      tasks/
```

用户分享的本地目录默认通过复制、同步或受控挂载进入房间工作区；原始个人目录仍归用户所有。多人 Bot 的正式修改和产出先写入房间工作区，不自动覆盖任何成员的个人目录。

第一期采用单向产物流：

```text
Bot 在房间工作区产出
  -> 服务端保存文件、版本和审计记录
  -> 房间成员看到产物卡片
  -> 成员点击“预览”或“下载”
  -> 文件复制到自己的电脑
```
