## 2. 产品结论

用户面对的是统一的“会话”，而不是三套互相割裂的入口：

| 场景 | 用户感知 | 运行时边界 |
| --- | --- | --- |
| 没有 Bot | 普通会话 | 现有单 AgentSession / 单 Run |
| 加入 1 个 Bot | 直接和这个 Bot 对话 | 尽量复用普通会话的单成员路径 |
| 加入 2 个以上 Bot | 融合会话 | RoomSession、协调者、任务和 A2A |
| 多个用户加入 | 多人融合会话 | 服务端权威 RoomSession |
| 正式会话临时 @ 未加入 Bot | Bot 悬浮侧窗 | 独立 SidecarSession，通过 proposal bridge 回主会话 |

关键交互规则：

- 第一个 Bot 可以直接承接普通消息。
- 加入第二个 Bot 后，第一个仍在席位中的 Bot 默认是协调者。
- 用户没有 `@` 时交给协调者；用户明确 `@` 时路由到指定 Bot。
- Bot 内部协作使用受控 mailbox/task/approval，不把隐藏 prompt 或内部思维链直接写入公共时间线。
- 侧窗可以读取主会话的公开投影，但只能通过桥接提案请求主会话采用，不能直接写主会话消息。
- 加入房间的 Bot 是当时配置的 `RoomBotSeat` 副本，不是 BotProfile 本体；删除席位不删除 BotProfile。
- Bot 的长期记忆是小而精炼的持久知识：candidate 不进入 prompt，只有用户确认后的 active memory 才允许检索。

## 3. 当前已经落地的真实能力

### 3.1 本地统一会话和 Bot

- 普通会话、融合会话、Bot sidecar 使用同一套主 UI 入口和主题系统。
- 角色库与 Bot 库分开：角色卡仍然是角色/提示配置，Bot 是拥有配置版本、模型/渠道、工具能力和长期记忆的可复用实体。
- Bot Library 已有配置副本和 candidate/active 记忆边界；加入融合会话时固定 `configRevisionId` 和快照字段。
- Sidecar 支持打开、关闭、最小化、吸边、拖拽和通过 IPC 把 proposal 交给主会话；侧窗不直接污染主会话时间线。

### 3.2 Room authority

`packages/core/src/collaboration/fusion-room-authority.ts` 是 RoomSession 的领域真值，当前快照包含：

- roomId、ownerUserId、status、title、goal；
- humanMembers、botSeats、botOwnerConsents、coordinatorSeatId；
- workspace、messages、events、usage；
- files、locks、runs；
- tasks、artifacts、approvals、mailbox。

已实现并有测试的 authority 能力：

- 人类成员邀请、接受、离开、移除、presence；
- Bot seat 加入、移除、owner consent、协调者继任；
- 用户消息和成员消息，目标成员、回复链、rootMessageId、幂等；
- title/goal owner-only 更新，旧快照兼容恢复；
- task 创建、严格状态迁移、版本 CAS、幂等；
- artifact 发布，路径安全、内容大小、sha256/byteSize、task 关联；
- 用户审批 request/resolve；
- A2A mailbox send/reply，深度、自环、root、causation、requestId 和 payload 限制；
- run start/await/finish，fence、triggerMessageId、awaiting_peer、awaiting_user、blocked；
- usage 账本和 Bot owner 费用归属字段；
- workspace 短锁、expected SHA、单文件/批量提交；
- workspace delete/move：删除 tombstone、移动双锁、拒绝覆盖、幂等。

### 3.3 Host、Gateway 和远程 RoomSession

- `packages/core/src/collaboration/fusion-room-host.ts`：按 roomId 管理 authority，统一 dispatch、snapshot save、事件通知和工作区事务回滚。
- `packages/core/src/collaboration/fusion-room-gateway.ts`：远程 wire action；`actorUserId` 由 authenticated principal 注入，renderer/wire payload 不能伪造身份；幂等键按动作和用户隔离。其 `defaultAuthorize` 已委托 P0-1 协议层 `decideRoomAccess`（见 `fusion-room-acl.ts`）。
- `packages/core/src/collaboration/fusion-room-http-client.ts`：远程快照、action、SSE cursor 和已发布文件下载。
- `apps/electron/src/main/lib/collaboration/fusion-room-runtime.ts`：显式组装 snapshot store、invite token、workspace store、HTTP/SSE transport、execution bridge 和默认 host tools。
- `apps/electron/src/main/lib/collaboration/fusion-room-http-server.ts`：认证后才允许读写；文件下载只允许 authority 明确 `downloadable === true` 且未删除的文件。
- 远程页面只通过 `FusionRoomViewModel` 和 `FusionRoomActionAdapter` 消费；页面不持有 authority、不接收 actorUserId、不做调度。
- 打包版网络入口当前仍然关闭。不要为了“先能连”而打开未经真实账户认证、证书生命周期和跨用户 ACL 设计的公网入口。

### 3.4 执行桥和 Bot 工具

`apps/electron/src/main/lib/collaboration/fusion-room-execution-bridge.ts` 当前支持：

- 用户消息按 `@`、coordinator、首个 Bot 路由；
- member-message、send-mailbox、resolve-approval、reply-mailbox 触发后续 Bot；
- Bot A `room_ask` -> A 等待 -> Bot B 被触发 -> B `room_reply` -> A continuation；
- `waitForIdle()` 动态 drain，等待运行期间新加入的 continuation；
- `FusionRoomHost.recoverInterruptedRuns()` 在 runtime 启动时把上次进程仍为 running 的 run 安全标成 blocked，不自动重放可能已经发生外部副作用的 run。

`apps/electron/src/main/lib/collaboration/fusion-room-host-tools.ts` 当前工具：

- `room_send`、`room_ask`、`room_reply`；
- `room_task_assign`、`room_task_update`、`room_publish_artifact`、`room_request_user`；
- `workspace_read_file`、`workspace_search`、`workspace_write_file`、`workspace_apply_patch`、`workspace_run_command`；
- `workspace_delete_file`、`workspace_move_file`。

工具的 roomId、seatId、runId、fence、actor 和权限由闭包/authority 提供，模型只能提供业务参数。写工具必须满足 Bot 的 `workspace-write` 权限、owner consent、当前 running run 和有效锁。

### 3.5 工作区和产物

- `apps/electron/src/main/lib/collaboration/fusion-room-workspace-store.ts` 将 RoomWorkspace materialize 到房间独立目录。
- 路径必须是安全相对路径；禁止 `..`、绝对路径、反斜杠和符号链接穿越。
- 写入使用临时文件和 atomic rename；delete 只允许普通文件；move 拒绝覆盖目标并支持 rollback。
- authority 的 deleted 文件只保留 tombstone 供冲突保护；renderer 和下载接口过滤 tombstone。
- 其他用户要获得实际产出，使用服务端已发布文件的下载，而不是默认反向同步到个人磁盘。

## 4. 重要安全不变量

以下规则不能为了测试方便或“先跑起来”而放宽：

1. renderer 不是调度器，也不是任何真值源。
2. 普通会话升级为多人融合会话时派生 RoomSession，不原地改变私有会话可见性。
3. Bot seat 是配置副本；BotProfile 的私有历史和 active memory 不因入房间公开。
4. Bot owner consent、room policy、task scope、resource grant 和运行权限取交集。
5. 所有公共消息、任务、产物、审批、mailbox 和文件元数据都必须经过 authority/Host。
6. 用户/网络输入不能提供 actorUserId、room owner、fence、depth、causation 等安全字段。
7. A2A 必须有 root、causation、深度和预算边界；禁止自环和无限互聊。
8. 文件必须经过安全路径、锁、expected SHA 和事务；禁止工具直接写物理路径。
9. 无法确认外部副作用时，重启恢复必须标记 blocked 或等待用户决定，不自动无限重放。
10. 未确认 candidate memory、侧窗未确认内容、私聊历史和未授权文件不能进入 Bot prompt。

## 8. 推荐继续开发顺序

不要先打开公网入口，也不要先重写 UI。推荐顺序：

1. 先为认证/ACL 写协议和测试：principal、room scope、Bot owner consent、resource grant、费用主体。
2. 用内存/本地 fixture 做两个用户、两个 Bot owner、一个共享工作区的 HTTP/SSE E2E。
3. 完成证书和打包网络配置后，再把 packaged gate 变成显式用户操作；默认仍关闭。
4. 实现持久 continuation 的“可观察 outbox + 用户确认 resume”，先不自动执行有未知副作用的旧 run。
5. 接入真实 Pi/KSCC provider adapter，分别验证 session 生命周期和工具桥；不能用模型选择器存在来代替 provider E2E。
6. 最后补完整远程 UI、分页、Bot handoff、memory consolidation E2E。
