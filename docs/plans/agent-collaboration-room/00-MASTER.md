# Agent 协作室：产品与架构总纲

> 状态：方案定稿，待分阶段实现
> 日期：2026-08-11
> 决策：[ADR-0007](../../decisions/ADR-0007-agent-collaboration-room.md)
> 详设：[01 UI/UX](./01-PRODUCT-UX-SPEC.md) · [02 Runtime/A2A](./02-RUNTIME-A2A-SPEC.md) · [03 实施计划](./03-IMPLEMENTATION-PHASES.md)

## 1. 一句话目标

在主 Rail 增加独立的 **“协作”** 入口，提供一个由用户、协调者和多个独立 Agent 组成的持久聊天室：用户可以聊天、点名、指派和旁观；Agent 可以并行工作、互相提问、交接产物；系统对任务、消息、权限、成本和因果链进行可审计的编排。

它不是普通会话的一次发送模式，也不是把看板套上一层聊天皮肤。

## 2. 我们最终要做成什么

```text
Rail：会话｜协作｜插件｜记忆｜角色库
                 │
                 └─ Agent 协作室
                    ├─ 房间侧栏：房间列表、未读、阻塞、运行状态
                    ├─ 房间时间线：用户/Agent 对话 + 重要运行事件
                    ├─ 成员与任务面板：成员状态、任务、产物、预算
                    └─ 独立成员运行时：各自模型/CLI/上下文/权限/工作区
```

目标体验：

1. 用户新建房间，选择工作区、目标和成员班底。
2. 每个成员有稳定身份、职责、模型/CLI 和独立逻辑会话。
3. 不点名时由协调者响应；`@成员` 直接投递；用户可显式创建任务或附加现有看板。
4. Agent 在执行中可通过受控 A2A 工具提问、回复和发布产物。
5. 多任务可并行；同一成员默认串行；冲突、等待、失败和成本都可见、可暂停、可恢复。
6. 用户离开页面后房间仍可工作；重启后可恢复房间、任务与未处理信箱。

## 3. 与现有能力的关系

| 能力 | 回答的问题 | 生命周期/真值 | 与协作室的关系 |
| --- | --- | --- | --- |
| 普通会话 | “我和一个主 Agent 聊什么？” | session 消息 | 保留；不承担团队运行 |
| 会诊 | “多个模型各自怎么看？” | 单次并行结果 + 汇总 | 可从房间发起，但不等于成员 |
| 圆桌 | “多个席位如何讨论出共识？” | 有界多轮讨论 | 保留为无工具的“议”；不升级为数字员工 |
| 子代理 | “把一件短活临时委派出去” | child run | 可作为成员内部执行手段，不能替代房间成员 |
| 看板/班组 | “长期任务当前真实状态是什么？” | board/task DB | 可选挂载到房间；仍是任务真值源 |
| CLI worker | “具体由哪个本地执行器干活？” | 一任务一进程 | 作为成员运行后端；逻辑成员持久，物理进程可短命 |
| 协作室 | “团队如何持续沟通与协同交付？” | room/member/message/mailbox/run | 新增独立容器和协作真值 |

关键组合原则：

- **房间是沟通与审计层**：谁向谁说了什么、为何触发、当前在等谁。
- **看板是任务真值层**：任务状态、依赖、验收和交付物不能只存在聊天里。
- **CLI worker 是执行层**：进程可以按需启动和退出，不要求为每个成员永久占用 PTY。
- **普通会话是个人入口**：主 Agent 可以建议“创建协作室”，但不能把当前会话暗中变成房间。

## 4. 第一版产品边界

### 4.1 MVP 必须有

- Rail 独立入口、房间列表、创建/归档房间。
- 每房间一个协调者和 1–6 个成员；成员绑定角色、模型或本地 CLI。
- 房间消息、`@成员`、成员状态、运行取消与错误恢复。
- 独立逻辑成员会话；每次唤醒可使用短命进程执行。
- 异步 A2A 信箱：发送、询问、回复、发布产物。
- 同一消息点名多人时并行扇出；同一成员一次只跑一个 turn。
- 深度、轮次、并发、时间和用量上限；完整因果链和审计事件。
- 绑定一个本地工作区；默认安全权限；并发写入需隔离或租约。
- 可选附加现有看板，但不强制每个房间都有看板。

### 4.2 MVP 明确不做

- 不做多人远程 IM、企业组织架构、排班/薪酬等“员工管理系统”。
- 不做 Agent 自由拉人、自由创建子房间或无限递归委派。
- 不承诺所有 CLI 都能在单个长驻进程中实时双工对话。
- 不允许模型绕过宿主直接调用其他 CLI、修改房间成员或扩大权限。
- 不让聊天文本成为任务完成与否的唯一依据。
- 不同时重做普通 Chat、看板和 CLI worker；只抽取可复用组件。

## 5. 核心产品原则

1. **入口独立，组件复用**：复用消息、Markdown、附件、工具过程、输入框和详情页；不复用普通 session 的生命周期和路由。
2. **逻辑常驻，物理按需**：成员身份、会话摘要和信箱持久；执行进程按 turn 唤醒。
3. **安静优先**：时间线默认只展示成员发言、关键状态和结论；细碎工具流折叠到 run 详情。
4. **显式路由**：无点名交给协调者；点名只唤醒目标；`@all` 是受限操作。
5. **任务与聊天分账**：聊天可引出任务，任务状态必须落看板/room task；两者用 ID 互链。
6. **人类可打断**：暂停房间、停止 run、修改优先级、回复等待、撤销成员都必须可操作。
7. **默认有界**：所有 A2A 都有深度、预算、并发和循环保护，失败时进入可解释状态。

## 6. 成功标准

MVP 不是“能看到多个头像”，而是下面的闭环真实成立：

```text
用户提出目标
  → 协调者拆出两个并行任务
  → Agent A 与 Agent B 分别执行
  → A 通过 A2A 向 B 请求一个接口约束
  → B 回复，A 从 awaiting_peer 恢复
  → 两者发布产物并回填任务
  → 协调者汇总，用户能追溯每一步因果和文件变更
```

验收指标：

- 每条 Agent 消息都能定位到 `roomId/memberId/runId/causationId`。
- 应用重启后，房间、成员、消息、任务链接和未处理信箱不丢失。
- A2A 链不会无限自激；超过边界后停止并说明原因。
- 两个成员不能在不隔离的情况下无提示地同时写同一文件。
- 用户可以在一个页面看清“谁在做、做什么、在等谁、花了多少、产物在哪”。

## 7. Hermes 参考：借什么，不借什么

本方案参考 `F:\hermes-studio` 的 group chat：房间成员持有 profile/provider/model/executor；按房间和成员构造稳定逻辑 session；从房间摘要、近期记录和当前消息投影上下文；同消息多目标并行扇出；用 mention depth 限制递归。

借鉴：

- room/member/message 三类持久实体。
- 每成员独立逻辑 session 与上下文投影。
- mention/A2A 路由、并行扇出、深度保护。
- 临时物理 session 执行后释放，逻辑身份继续存在。

不照搬：

- 远程多人配对、服务端 Python bridge、Koa/Socket 结构。
- 让群聊 Agent 自行开启更深层的后台导演。
- 将所有协作都塞进自由文本 mention 解析。
- 用共享目录直接承受无保护的并发写入。

## 8. 决策优先级

实现遇到冲突时按以下顺序取舍：

1. 数据与工作区安全。
2. 用户控制权和可恢复性。
3. 任务/消息因果可审计。
4. 状态一致性。
5. 交互简洁与组件复用。
6. 更实时、更像真人群聊的表现力。
