# 记忆质量与检索闭环

## 背景

当前记忆系统已经能从会话中产生 L0-L3 候选，也能把跨会话摘要写入 L4、把反思结果写入 L5。但“检测到候选”与“模型实际使用记忆”之间仍有断点：

- 重复检测主要在单个会话的最近消息上计数，同一条消息中的多个匹配可能被当成多次证据。
- L3 纠错使用正则命中的局部片段作为正文。命中“不是……”或“改成……”但消息尚未结束时，半句话也可能进入候选。
- L1 项目记忆曾以“同一 workspace 出现两次”作为充分条件，这只能证明项目被打开过，不能证明存在可复用的项目规则。
- 会话运行时的按需检索主要只查 L4；L3 纠错和 L5 洞察即使存在，也不会被当前问题召回。

因此，单条 L3 记录的意义不是“凭孤例直接改变模型行为”，而是作为带上下文的纠错证据：它必须先经过候选质量门禁和审批/整合，随后只在与当前问题相关时参与检索。孤例可以保留为候选，但不应无条件成为有效规则。

## 本次改动

1. 所有层级的候选正文增加“未完结片段”门禁，尤其拦截以“也、而、的、是、为、在”等连接词收尾的文本；L3 继续拦截已知的正则半截纠错。
2. L3 纠错候选保存用户消息中以句子边界截取的完整证据，而不是只保存正则命中的几个字；整合兜底仍不能绕过质量门禁。
3. L1 项目重复提高到至少 3 个会话，并要求标题之间存在主题词重叠，避免“打开同一个项目两次”直接生成项目记忆。
4. 按需检索同时支持 L3 和 L5，并保留 L4；检索结果按当前问题做词面相关性排序，未命中的全局记忆不注入 prompt。

## 记忆生命周期

```text
会话证据
  -> 候选（可带孤例，但必须有来源和上下文）
  -> 质量门禁（完整性、可读性、去重）
  -> stage 待审批 / consolidation 整合
  -> 有效记忆（L0-L3/L5）
  -> 按问题召回（L3/L4/L5）
```

其中：

- L0/L1/L2 的重复候选需要跨独立消息或跨会话证据；不能因为一条长消息里重复出现就升级。
- L3 的显式纠错可以由一次高信号事件产生候选，但必须保留“用户原话 + 前一条 AI 上下文”，并经过质量门禁。它表达的是“优先纠正某类默认推断”，不是无条件覆盖当前用户要求。
- L5 只表示跨会话模式或洞察，不能把一次会话摘要改写成洞察。
- 任何召回内容都不是系统指令；当前用户要求优先，且冲突的 L3 只能作为提示交给模型判断。

## 后续建议

本次先落地质量门禁和检索闭环。下一阶段再给每条有效记忆补齐 `scope`、`status`、`evidenceIds`、`createdAt`、`updatedAt` 等结构化字段，并将历史无范围记录标记为 legacy，而不是继续默认当作项目级记忆。长期还应引入基于 embedding 的语义召回和用户可见的“为何召回/依据是什么”。

## 第二阶段增量

- `NudgeCandidate`、`StageEntry` 和新写入的 L3 JSONL 现在带有 `scope`、`workspaceSlug`、`status`、`evidenceIds` 等字段；旧记录没有这些字段时按 legacy/global 兼容读取。
- L4 和 L3 召回会优先限制在当前 workspace；没有范围的旧 L4/L3 仍可读取，但不会被伪装成项目级记忆。
- correction toast 不再自动 accept。显式纠错首先是候选，只有用户确认后才写成 `active` L3。

这意味着截图中的孤例现在最多停留在“有来源的候选/证据”阶段；它既不能因为正则命中自动落盘，也不会在不相关项目的问题中被召回。
