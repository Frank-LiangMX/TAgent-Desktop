# ADR-0007：Agent 协作室采用独立 Rail 入口与独立运行时

> 状态：运行时边界已拍板；用户入口部分由 [ADR-0009](./ADR-0009-fusion-session-bridge-and-orchestration.md) 修订（2026-08-31）
> 模块：agent-collaboration-room
> 详设：[总纲](../plans/agent-collaboration-room/00-MASTER.md)

## 背景

TAgent 已有普通会话、会诊、圆桌、SubAgent、看板/班组和本地 CLI worker，但它们都不能完整表达“用户与多个独立 Agent 在一个持久房间里交流，Agent 又能并行执行并互相通信”的产品形态。

- 普通会话的 `@` 目前是主模型按角色顺序投影，不是多个独立成员会话。
- 圆桌是有界、无工具的讨论机制。
- 看板由主会话派工，擅长任务状态，不承担平等可见的团队对话。
- CLI worker 是一任务一进程的短命执行器，不是聊天室身份。

## 决策

新增一级产品容器 **Agent 协作室**：

1. 在主 Rail 使用独立“协作”入口，位于“会话”之后。
2. 使用独立的房间列表、页面路由、数据表、IPC 和运行时服务。
3. 房间成员拥有稳定逻辑身份与独立上下文；底层物理 CLI 进程仍可按 turn 短命运行。
4. 房间时间线是沟通与审计真值；任务状态继续由看板或 room task 真值维护。
5. A2A 通过宿主提供的结构化工具和异步信箱完成，不依赖自由文本 `@` 解析作为唯一协议。
6. 普通会话只能显式创建/打开协作室，不允许静默切换容器类型。

## 为什么不是普通会话里的一个模式

协作室和普通会话的差异不是 UI 开关，而是基础语义不同：

| 维度 | 普通会话 | 协作室 |
| --- | --- | --- |
| 参与者 | 用户 + 一个主 Agent | 用户 + 协调者 + 多个独立 Agent |
| 路由 | 当前模型回答 | 点名、信箱、任务和因果路由 |
| 生命周期 | session turn | room/member/run/task 多层生命周期 |
| 并发 | 单主线 | 多成员并行、成员内串行 |
| 真值 | 消息 | 消息 + 成员状态 + 信箱 + 任务链接 |
| 安全 | 单运行上下文 | 并发写冲突、递归 A2A、预算放大 |

把它做成 composer 菜单会隐藏这些状态，使用户误以为只是“换一种回复方式”，也会迫使普通 session 承担不兼容的恢复和并发语义。

## 允许复用的部分

- AppShell、Rail 按钮形态、消息气泡、Markdown/附件渲染、输入框、工具过程卡、权限横幅、详情页导航。
- 角色库、模型/渠道选择、CLI worker runner、看板 task/worker 能力。
- 全局通知、状态 ticker、工作区注册和文件预览能力。

复用组件不等于复用真值源。禁止让 room message 直接伪装成普通 session message，或让 room member 伪装成一个 role mention。

## 后果

正面：

- 用户心智明确；能承载持久团队和 A2A。
- 普通 Chat 不被复杂状态污染。
- 可以渐进接入现有看板和 CLI worker，而不推翻它们。

代价：

- 需要新增房间数据库、事件路由、调度器、恢复机制和专属 UI。
- 必须处理并发写、安全权限、预算放大和消息循环。
- 组件虽能复用，页面状态和 IPC 不能简单复制 Chat。

## 被否决的方案

| 方案 | 否决原因 |
| --- | --- |
| 普通会话发送菜单新增“协作室模式” | 隐藏了独立生命周期、并发与恢复语义 |
| 完全用看板表达团队协作 | 任务很清楚，但成员间对话、追问和用户在场感不足 |
| 把圆桌席位赋予工具 | 破坏“议/干”边界，且当前席位是无状态单发 |
| 为每个成员永久保持 CLI 进程 | CLI 协议能力不一致，资源和恢复成本过高 |
| 只解析消息里的 `@` 实现 A2A | 协议脆弱、无法可靠表示回复、等待、因果和权限 |
