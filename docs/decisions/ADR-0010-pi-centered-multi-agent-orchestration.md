# ADR-0010：Pi 主核与原生协议配角 Agent

> **后续决策（2026-09-16）**：[ADR-0011：三内核工作台](./ADR-0011-three-runtime-agent-workbench.md) 取代本文“Pi 唯一主会话、其他仅为配角”的限制。Pi 默认且可定制，Codex 与 Claude Code/KSCC 可处理主会话。下文保留历史；模型/Agent 区分与原生协议边界继续适用。

> 状态：方向确认（2026-09-16）  
> 相关决策：[ADR-0004：SubAgent / 看板 / MoA 边界](./ADR-0004-multi-runtime-mechanism-boundaries.md)、[ADR-0009：融合会话桥接与编排](./ADR-0009-fusion-session-bridge-and-orchestration.md)

## 背景

公司 API Key 已可供 TAgent 直接调用。Pi 核可以负责主会话、模型请求、工具循环、上下文管理和调度；Codex、Claude Code、KSCC 等则可利用各自成熟的 Agent Loop 和工具能力。

这些 Agent 的会话协议、工具协议、上下文恢复和事件格式不同。把它们改造成同一个 Agent，或让它们都能替换主会话，会扩大协议适配面并削弱 Pi 主线的可控性。

Hermes Studio 的可借鉴点是：宿主管生命周期与运行记录，各 Agent 保留自己的运行时和协议；只在宿主边界归一状态与结果。TAgent 不需要复制其完整 Provider Proxy 或所有 Runtime。

## 决策

### 1. Pi 是唯一主会话与编排核

```text
用户 ↔ Pi 主会话
        ├─ 调用已配置渠道中的模型（如 Grok、Claude、GPT）
        ├─ 发起 MoA 会诊
        └─ 派发执行任务给 Codex / Claude Code / KSCC 等
```

主会话历史、上下文压缩、工具循环和最终回复由 Pi/TAgent 管理。外部 Agent 不切换为主会话，不要求其原生会话格式进入 Pi 的上下文。

### 2. 模型与执行 Agent 是不同概念

- **模型**通过已配置渠道/API Key 被 Pi 或 MoA 调用；例如 Grok 是模型时，不因此成为独立执行 Runtime。
- **执行 Agent**拥有自己的工具循环和协议；例如 Codex、Claude Code、KSCC。TAgent 派发任务并管理进程，不重写它们的内部协议。
- 是否存在对应 CLI、是否支持某项能力，在派发前显式检测；KSCC 保留为可插拔兼容后端，不作为主线默认依赖。

### 3. 只统一宿主运行契约，不统一内部协议

每个执行 Agent 通过独立 Adapter 接入，保留原生启动、流解析、恢复与取消语义。Adapter 向 TAgent 提供最小公共能力：

- 启动、取消、状态与错误；
- 可选的文本/进度/工具事件；
- 最终摘要与可识别的文件产物。

缺失或无法可靠映射的能力标记为“不支持/未知”，不得伪造统一行为。完整原生输出可在任务详情中查看；Pi 主上下文只接收必要进度和最终结果。

### 4. 配置按职责分层

- **渠道与模型**：API Key、Provider、模型 ID、上下文容量等，沿用现有渠道配置。
- **执行器配置**：Codex、Claude Code、KSCC 的安装/路径、启用状态及其原生运行选项。
- **角色与派工偏好**：任务类型、提示词、权限和工作区约束；第一阶段复用现有角色库与 CLI worker 配置，不另造一套 Profile 存储。
- **单次任务覆盖**：仅覆盖本次明确允许变化的选项。
- **运行快照**：派发时记录实际 Agent、工作区、权限和配置版本，运行期间设置变化不追溯影响任务。

先将现有 CLI 工人池整理为可理解的执行 Agent 入口，再按使用反馈增加更完整的自定义 Agent 配置；避免一开始建设庞大的通用 Profile/插件系统。

### 5. 交互保持在现有会话和调度入口

- 普通对话始终由 Pi 处理。
- 用户可在当前会话显式委派给一个或多个已启用的执行 Agent；自动派工由 Pi 决定，但受设置中的启用、权限和能力约束。
- MoA 用于多模型分析、比较和汇总；Codex/Claude Code 等执行 Agent 不作为 MoA 模型席位。
- 子任务显示为运行卡：主时间线展示状态、简要进度和结果；完整原生事件放在可展开详情中。
- 长任务、依赖和跨重启恢复仍走看板/协作室等既有运行容器，不用普通 SubAgent 伪装长生命周期任务。

## 分阶段落地

1. **稳固 Pi 主线**：确认 API 渠道、上下文窗口/压缩、task 与 MoA 信息流；避免无关的重复内容写入历史。
2. **统一外层任务管理**：为现有 Pi 子代理、Codex、Claude Code、KSCC 规范状态、取消、摘要与详情入口；各 Adapter 继续使用原生协议。
3. **改进自定义派工**：基于现有角色和执行器配置，让用户配置“什么任务交给谁、权限/工作区是什么”，再决定是否需要独立 Agent Profile。
4. **逐个扩展 Runtime**：每新增一种外部 Agent 都提供能力声明、安装检测、取消行为和协议回归测试；不因 UI 统一就宣称能力等同。

## 暂不做

- 不允许 Codex、Claude Code、Grok 或 KSCC 替换 Pi 成为主会话核。
- 不把外部 Agent 的内部消息、工具协议、上下文和压缩机制重写成 Pi 协议。
- 暂不建设通用 Provider Proxy、任意 CLI 执行器或完整可视化 DAG 工作流。
- 不将模型（如 Grok API）与 Agent Runtime（如 Codex CLI）混为一个选项。

## 后果

正面：Pi 主线与上下文行为保持稳定；能够渐进接入成熟外部 Agent；协议故障被限制在对应 Adapter；KSCC 可保留而不再绑住架构。

代价：不同执行 Agent 的能力和详情不完全一致；Adapter 仍需逐个维护；运行快照、权限边界和原生会话恢复必须按 Runtime 分别验证。

## 验收原则

1. 更换外部执行 Agent 不改变主会话协议、历史和 Pi 工具循环。
2. 外部 Agent 的停止/失败不会让父会话永久挂起；结果只回投一次。
3. 运行卡能解释执行者、状态、工作区和最终结果；详情不污染主上下文。
4. 未支持的能力明确显示，不静默降级或伪造成功。
5. 关闭或移除 KSCC 后，Pi、API 模型调用和其它执行 Agent 仍可工作。
