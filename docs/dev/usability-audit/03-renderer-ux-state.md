# 渲染层会话体验审计（TAgent vs Proma）

> 只读审计，未改任何代码。聚焦「基础使用都做不到」在**渲染层 / 会话运行态 / 状态机**上的根因。
> 对照仓库：`F:\Proma`（基线，可干活）vs `F:\TAgent-Desktop`（被审）。
> 用户数据证据：`C:\Users\liangmingxuan\.tagent-dev\projects\` 下最新 session `*.messages.jsonl`。
> 权限链路根因见同目录 `01-permission-tools.md`；Pi 运行时/流式见 `02-pi-runtime-stream.md`。本文不重复，只补渲染/状态层。

## 结论摘要（5 条内）

1. **权限横幅没有「已决」回听通道 → 30s 超时后 banner 是死的**：IPC 只有 `PERMISSION_REQUEST`（主→渲染）与 `PERMISSION_RESPOND`（渲染→主），**没有** `PERMISSION_RESOLVED`（主→渲染）（`shared/types/agent.ts:2060/2062`）。主进程 30s 超时自动 deny 后从 `pending` 删掉（`permission-service.ts:119-124`），但渲染层 `PermissionBanner` 只 `onPermissionRequest` 订阅（`PermissionBanner.tsx:25-32`），收不到「已自动拒绝」通知 → banner 一直挂着；用户事后点「允许」时主进程 `pending` 已空，`registerIpc` `if (!p) return` 静默空操作（`permission-service.ts:271-272`），按钮是死的。Proma 的 `PermissionBanner` 由 `allPendingPermissionRequestsAtom` 队列驱动，`permission_resolved` 事件出队，天然不会卡（`agent-atoms.ts:516`、`useGlobalAgentListeners.ts:1034`）。
2. **权限横幅是单槽 `useState`，并发请求后到先丢 + 切会话 remount 丢 pending**：`PermissionBanner` `const [req,setReq]=useState<PermissionReq|null>(null)`，新请求 `setReq(pr)` 直接覆盖（`PermissionBanner.tsx:23/28-29`）。组件挂在 `key=sessionId` 的 `<Chat>` 树里（`session-run-atoms.ts:8` 注释：SessionRouter key=sessionId 切 tab 卸载实例），切走再切回 `req` 重置为 `null`，而主进程 `pending` 仍在等 30s 超时 → 用户回来看到空 banner，请求静默被 deny。Proma 是全局 atom `Map<sessionId, PermissionRequest[]>` FIFO，显示 `requests[0]` + `(+N)`，跨会话存活（`PermissionBanner.tsx:39/133`、`agent-atoms.ts:516`）。
3. **ZodError 权限层回归，用户实测 15 次，banner 根本没走到**：最新会话 `session-1785899943685.messages.jsonl` 里 15 条 `Tool permission request failed: ZodError`（`path:["updatedInput"] expected record, received undefined` + 畸形 deny 分支），由 `Bash`(heredoc / `python -c`) 与 `Write` 触发——kscc SDK 的 `canUseTool` 返回值缺 `updatedInput`，Zod 联合类型运行时校验整次权限失败，用户看到的是工具结果里的内部校验错，**不是** Allow/Deny 横幅。工作树已修（`permission-service.ts:314` `return { behavior:'allow', updatedInput: input }` + 第 283-290 行注释明言此 bug，git status 显示该文件 `M` 未提交），但用户跑的版本仍带此 bug。assistant 自己在流里都承认「这是 harness 权限层在本次会话里的一个内部 bug」。
4. **无 idle 兜底 reconcile → 中断/崩溃的 run 卡在 `running:true`**：`useGlobalSessionRunSync` 只在 `result` / `session_error` 时 `stopSessionRun`（`useGlobalSessionRunSync.ts:40-48`），`Chat` remount 时**故意不按 `getSessionStatus=idle` 清 atom**（`Chat.tsx:577` 注释 + `583-589` 仅在主进程仍 `running` 时 adopt）。若一轮被用户打断/通道断流且主进程没发 `result`/`session_error`，atom 永远 `running:true`，计时 pill 卡死、停止键常驻。用户数据里最新会话末行正是 `"[Request interrupted by user]"`、注册表 `status:"idle"` + `stoppedByUser:null`（既非正常结束也非用户停止的歧义态）——正是这个兜底缺失的目标场景。Proma 以 `STREAM_COMPLETE` 为唯一释放源 + `startedAt` 过期跑保护 + 全局监听常驻根（`useGlobalAgentListeners.ts:1184/1192`），且有 `backgroundWaiting` 软闲态兜底。
5. **错误渲染是扁平 assistant 文本气泡，无 copy/retry/dismiss/重试进度**：`Chat.tsx:1247-1264` 的 `session_error` 分支把错误塞成一条 `type:'assistant'` 的 `text` 气泡（`detail = title：message（可重试）`），没有复制按钮、没有重试按钮、没有重试进度机。Proma 有独立 `agentStreamErrorsAtom` banner（copy + dismiss）、`RetryingNotice` 退避倒计时 + 逐次尝试历史、非成功 `resultSubtype` 的 toast（`agent-atoms.ts:1121`、`AgentMessages.tsx:232`、`useGlobalAgentListeners.ts:1237-1252`）。TAgent 用户遇到 API/限流/校验错时，只能把错误当普通消息读、手动重新打字发送。

## 修复顺序（只列 P0/P1，不动代码）

1. **加 `PERMISSION_RESOLVED` 主→渲染通道，让横幅与主进程状态一致**（P0，根因）：主进程在 `askRenderer` 的 30s 超时自动 deny、以及 `PERMISSION_RESPOND` 处理完时，都向渲染发 `PERMISSION_RESOLVED {reqId, behavior}`；`PermissionBanner` 订阅它，按 `reqId` 清掉当前 `req`（即便用户没点）。这样 30s 后 banner 自动消失、用户不再点死按钮。`shared/types/agent.ts:2060/2062` 加通道，`permission-service.ts:119-124` 与 `:271-280` 发事件，`PermissionBanner.tsx:25-32` 加监听。
2. **横幅改全局 atom 队列（per-session FIFO），不再单槽 useState**（P0）：对齐 Proma `allPendingPermissionRequestsAtom`，`Map<sessionId, PermissionRequest[]>`，渲染 `requests[0]` + `(+N)`；切会话/ remount 都不丢。顺带解决「并发请求后到先丢」与「切走再切回 pending 静默 deny」。`PermissionBanner.tsx:22-37` 整段重写为 atom 派生。
3. **提交并验证 ZodError 权限层修复**（P0，已在工作树）：`permission-service.ts:314` 的 `updatedInput: input` 与 deny 分支 `message` 守卫已对，但 git `M` 未提交、未发版，用户实测版本仍带 bug。需提交 + 用最新会话同类输入（`Bash` heredoc / `python -c` / `Write`）回归，确认不再吐 `ZodError`、正常弹 Allow/Deny。
4. **加 idle 兜底 reconcile / 看门狗**（P1）：`Chat` remount 时若 `getSessionStatus=idle` 而 atom 仍 `running:true`，应 `stopSessionRun`（或 `softStop` 保留计时但清 running，避免停止键常驻）；另在 `useGlobalSessionRunSync` 加「最近 N 秒无流式事件且主进程 idle」的看门狗兜底。`Chat.tsx:577-589` 改判 + `useGlobalSessionRunSync.ts` 加超时兜底。用户数据的中断态会话正是此场景。
5. **错误渲染升级为 banner + 重试**（P1）：`session_error` 不再塞扁平 assistant 气泡，改为独立错误条（copy + dismiss + 「重试」按钮，重试按上一条 user 输入重发）；对齐 Proma `agentStreamErrorsAtom` + `RetryingNotice`。`Chat.tsx:1247-1264` 替换为错误条组件。
6. **流式终态不单靠 `stop_reason`，落 `result`/`turn_end` 兜底硬化**（P1）：`sdk_message` 路径已靠 `turn_end`/`result` 兜底清 `streaming`，需补「收到 `result` 时强制把所有 `streaming:true` 项标 false」的 finalize（`Chat.tsx:1153-1167` 已部分做，确认覆盖 tool_use 悬挂项）；并推动新会话格式补写 `result` 终止信封（与 02 报告协同），消除「末行悬挂 tool_use + stop_reason:null」的歧义态。
