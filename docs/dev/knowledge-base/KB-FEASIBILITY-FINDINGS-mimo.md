# KB 可行性评审 · mimo

> 立场：UX / 用户心智 / Agent 行为 / MVP 裁剪  
> 评审对象：TAgent Desktop 新建「知识库」子系统 brief  
> 对照：`docs/memory/master-design.md`（L0–L5）+ `docs/memory/handoff.md`（已落地能力）

---

## 一句话结论

**产品方向对（用户确实需要「参考书」式的项目档案，与 L0–L5 自动沉淀记忆分离），但当前 brief 的范围、命名、心智边界在用户视角下都偏重——我主张 Phase 1 只做「库 + 直存整档 + 检索注入」三件套，把策展/增量成稿/多视图全部延后到验证用户真实使用节奏之后。**

---

## 可行性评级（产品/技术/集成 各 1–5 分 + 一句理由）

| 维度 | 分数 | 理由 |
|---|---|---|
| **产品** | **4 / 5** | 用户痛点真实（规范/成稿/参考资料需要「专门放」），但 brief 把「库」和「策展工作流」混在一个需求里，心智门槛偏高 |
| **技术** | **4 / 5** | SQLite + FTS5 + blobs + 可选向量在 Electron 里已经验证（master-design §3 L4 FTS5 已在跑）；Office/截图 ingestion 是工程量问题不是技术风险 |
| **集成** | **3 / 5** | 与 L0–L5、BotMemory、协作室、8k 协调器的隔离边界 brief 没画清楚，落地时容易和现有 prompt 注入链路抢「回答规范类问题」优先级 |

---

## 核心建议（5 条，按优先级）

1. **把 KB 的产品定位写成一句用户能复述的话**：「我给 Agent 一本项目专属的参考书，它比记忆更稳、比附件更好找」。当前 brief 的描述对工程友好、对用户不友好——UX 视角下必须先有一句对外话术，否则用户建库后不知道什么时候该往 KB 写、什么时候该等 L5 沉淀。

2. **MVP 砍到只做三件事**：(a) 创建库（命名 + 模板选其一）；(b) 直存完整文档（拖入 Word/Excel/PPT/图片/MD/链接）；(c) 会话侧 `@kb` 检索 + 注入（KB 优先于 L5 答规范）。**素材池、Agent 策展、增量成稿、多视图导出——四项全部砍掉**，留到验证用户实际使用节奏之后。

3. **复用而非新建「库内整理」的人机节点**：brief 的「Agent 找上下文、去重、合并、写过渡、补结构」听上去漂亮，但用户已经能在 L5 的 Nudge + idle consolidation 里看到「Agent 也会乱写」。**KB 阶段不该引入新的 Agent 自主写权限**——所有写入都要走显式 confirm，且每条都打 user/agent 来源标签。

4. **「库」心智要先于「视图」心智**：用户在第一次见到这个能力时，脑子里出现的不是「我要一份脑图」，而是「我手上有 30 份规范文档，得有个地方放」。**MVP 必须先让「归位」行为可感知**——建库后第一动作是「把这堆东西分门别类塞进去」，而不是先看脑图。

5. **检索优先级用一句话写死**：「用户问『我们规范怎么说』→ KB 优先；用户问『上次我们聊到哪』→ L5 优先；用户问『把这两件事合一下』→ 两者一起拿」。这条规则不进 phase-1 验收，但必须在 brief v2 里写清楚，否则会和 L-rag 抢注入位。

## 推荐 MVP 范围

### ✅ 做（Phase 1，约 2–3 周）

- 库（Library）：用户命名、选模板（规范 / 架构 / 开发笔记 / 参考资料 / 待整理 五选一即可，模板只影响「条目缺省归类」）
- 条目（Item）：直存完整文档（Word/Excel/PPT/MD/图片/PDF/链接），原文件 + 元数据 + FTS5 索引
- 检索与会话注入：会话侧 `@kb <库名>` 命令；自动判定「用户问的是规范类」时把 KB 命中片段注入 system prompt 末尾（**不进 L-fact 区，避免污染 cache**）
- 一处 UI：库列表 + 条目列表 + 预览（不提供脑图/表格/Word 导出）

### ❌ 不做（明确推迟）

- **素材池（Source/Fragment 两层）** —— 用户根本没有「一页截图 + 几句话」的高频场景，先用「直接存整份」满足 90% 用例
- **Agent 策展（自动归类/合并/补过渡）** —— 与 L5 consolidation 行为重叠，会让用户分不清「这个是被 KB 整理的还是被 memory 整理的」
- **增量成稿与版本** —— 没有「成稿」心智之前强行做版本，等于把 Git 复刻一遍；用户要的是「文档存放 + 检索」，不是「文档协同」
- **多视图输出（脑图/Word/表格）** —— 存储层只保留 canonical（原文 + 元数据 + FTS5），视图导出放 Phase 3+ 看真实使用频次决定
- **sqlite-vec / 外部向量库** —— FTS5 + 关键词 + 标签先够用；向量检索在「成稿量 > 500 条」时再评估

## 主要风险与对策

| 风险 | UX/心智层面的具体表现 | 对策 |
|---|---|---|
| **「记忆 vs 知识库」分不清** | 用户问「我们规范」时被告知「这是 KB，不是 memory」——他只想要答案 | 入口文案改「项目参考书」；不向用户暴露 L0–L5 概念 |
| **KB 注入污染 cache** | KB 命中片段进 system prompt 区，破 prompt cache 稳定命中（D8 反模式） | KB 命中走 messages 区头部，复用 L-rag 注入路径 |
| **Agent 越权整理** | 用户随手丢进素材池，Agent 自动合并了规范文档 | MVP 不开 Agent 写入；所有写操作走用户点确认 |
| **库膨胀** | 一开始建 10 个库，每个 200 条，半年后检索不到东西 | Phase 2 加「最近使用 / 高频引用」排序，不做标签云 |
| **Office/截图 ingestion 慢** | 用户拖 50M PPT，进度条卡 30 秒，体感炸裂 | 后台 ingest，前端显示「解析中…可在 KB 面板看到状态」；不进同步路径 |
| **与 L-rag 抢优先级** | L5 答过的和 KB 答过的结论不一致，Agent 串台 | 注入时显式标注来源（`[KB: 规范.md §3]` vs `[L5: 上次讨论]`） |

## 与 L0–L5 边界建议（具体规则）

| 场景 | 走 KB | 走 L5 | 都不走 |
|---|---|---|---|
| 「我们项目的代码规范是什么」 | ✅ 命中即答 | 兜底 | — |
| 「上次我们讨论过 X 吗」 | — | ✅ FTS5/L4/L5 | — |
| 「把这两份规范合并成一份」 | 引用 + 输出 | — | 写入走用户 confirm，不进 KB 也不进 L5 |
| 「我刚才截图了一段对话」 | 直存为条目 | — | 不让 L5 主动抽 |
| 「我说的『kscc 不准』是个事实」 | — | L2 候选 | 用户显式 Nudge 才升 L2 |

**硬规则**（写进 brief v2）：
1. KB 条目永远不进 L5 自动 consolidation
2. L5 的 L-rag 不读 KB；KB 的注入独立路径
3. 同一事实两边都有 → 以 KB 为准（KB 是用户显式给的，L5 是 Agent 推的），但 UI 要把这个判断告诉用户（避免「为什么答案变了」）

## 开源借鉴清单

只抄层、不 fork：

| 项目 | 借鉴层 | 不抄的原因 |
|---|---|---|
| **AnythingLLM** | 「库 + 工作区 + 文档解析 pipeline」的 UX 编排 | 它是 SaaS 套壳，重 Agent 编排 |
| **Dify** | 「数据集 / 文档 / 分段」的数据模型字段命名参考 | 太重，TAgent 不要 workflow |
| **RAGFlow** | 复杂文档（带表格/PDF）的 deepdoc 解析思路 | Java/Python 重型栈，不适合 Electron |
| **Khoj** | 「聊天整理入库」这个交互原型（用户原始诉求第 3 条的来源） | 它把 chat 当主入口，TAgent 的 chat 是会话不是归档 |
| **Obsidian + MCP** | 用户漏考虑的替代方案：纯文件夹 + frontmatter + MCP 检索 | 见 Q6 |
| **sqlite-rag / sqlite-vec** | 若后期要做语义检索，底层能力直接拿 | 现在不做 |

**强烈建议先看 Obsidian + MCP 路线**：如果用户主要诉求是「项目规范 + 参考资料 + 能搜」，那一个本地 Markdown 文件夹 + frontmatter 标签 + 一个 MCP 检索服务就够了，**根本不需要新子系统**。这条要在 Q6 里跟用户对齐，否则我们可能在做一个 30% 解决方案。

## 反对意见 / 若我是 devil's advocate

> 这是 mimo 必须写的部分。

1. **「不要做 KB 子系统，做一个 KB MCP server 挂到现有 L-rag 上就够」**——brief 的六层模型（库/集合/素材/片段/成稿/视图）在用户视角是过度设计。如果用户真正想要的是「项目规范能被搜到」，那么 (a) 一个本地 Markdown 目录 (b) frontmatter 标签 (c) 一个 FTS5 索引 (d) AgentTool 暴露给 pi/kscc——四个组件 200 行代码搞定，**不需要新的 library/collection/source/fragment/document/view 六层**。

2. **「素材池 + Agent 策展」是用户在抄 Notion AI / Anthropic Projects，不是真有这个需求**——他在 brief 里写「素材池（零散一页/截图/几句话，待 Agent 归类）」听起来很 fancy，但用户每天真正会出现「零散几页 + Agent 帮我整理」的场景，可能一个月才两三次。**MVP 做这个 = 90% 时间维护 10% 场景**。

3. **「KB 优先于 memory 回答规范类问题」是用户的直觉，但 LLM 不会真遵守**——brief 第 5 条说「KB 优先于 memory」，但 LLM 不读这个优先级声明，它读上下文拼接顺序。**真正该做的是把 KB 注入到 system prompt 固定位置 + 加 source 标签 + 在 Chat UI 显示「答案来自 KB」**，而不是寄希望于 prompt 文案。

4. **「多视图（表格/脑图/Word）」对 TAgent 用户群是伪需求**——TAgent 用户是「我自己管项目资料的人」，不是「我要把知识库分享给团队的人」。脑图/Wiki 导出是后者需求，**先把单用户场景跑通**。

5. **我可能错的地方**：如果用户其实有「多人协作 + 项目档案」的真实场景（虽然 brief 没写），那 Obsidian 路线就不够，确实需要带视图导出的完整 KB 子系统。**所以最大风险不是做多了，是做早了**——先做最小可用，跑两个月，看用户有没有主动要「成稿/版本/脑图」，没有就停在这里。

## 待用户拍板的问题（≤5 个）

1. **KB 的真实高频场景是「项目规范/参考资料」还是「多项目资料管理」？**——决定走「KB 子系统」还是「Obsidian + MCP 路线」。
2. **用户问「规范类问题」时，希望 KB 命中后是否在 Chat UI 显示来源标签？**——决定注入路径要不要带 source 元数据。
3. **Agent 在 KB 里能不能自动归类/合并？**——我建议 MVP 全部走用户 confirm，但 brief 暗示用户希望 Agent 主动做。需要明确边界。
4. **库的模板（规范/架构/开发笔记/参考资料/待整理）五个够吗？还是先只做「未分类 + 已分类」两档？**——UX 视角下两档更轻，但用户 brief 暗示要五档。
5. **MVP 验证期多长？**——我建议 6 周：3 周上线最小集，3 周观察用户真实使用频次，再决定要不要做策展/视图/成稿。

## 评审立场备注

按 brief §3 要求，mimo 偏 UX/用户心智/Agent 行为/MVP 裁剪：

- **与 kscc 可能 disagree**：kscc 视角下六层模型便于工程分期；我主张砍到 2 层（库 + 条目）。
- **与 grok 可能 disagree**：grok 会主张补竞品完整度（多视图、协作）；我主张先跑通单用户最小闭环。
- **共同点**：三人都会同意「不重做 L5、不污染 cache、不抢 L-rag 注入位」三条硬约束。

---

**最终立场：MVP 砍 50%，Phase 1 只做「库 + 直存 + 检索注入」，其余全部延后到 6 周验证后看真实使用频次再决定。最大的失败模式不是「做少了」，而是「按 brief 全做完后用户只用到了直存整档」。**
