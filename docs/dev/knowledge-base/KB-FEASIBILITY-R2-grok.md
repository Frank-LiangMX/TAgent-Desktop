# KB 圆桌 R2 · grok

## 读后总评（一段：对方哪里说服了你 / 哪里仍不同意）

读完 SYNTHESIS 分歧表与 kscc / mimo 全文后，我在「首发厚度」上被双方共同说服：**把素材池与半自动归类捆进 P1–P2 首发赌注，确实会触发我自己写过的 R-KB6（未完成绑定+检索+确认入库就开策展 Agent）**，也踩中 mimo「最大失败不是做少了，是做早了」的判断。kscc 把 Phase 1 钉成「库+MD/文本+FTS+@kb+candidate 门控骨架」比我原先的 P1–P2 捆绑更可交付，也更不容易把 Desktop 主线拖死。但我仍不同意 mimo 把「自建子系统」降格为可有可无的 Obsidian/文件夹 + MCP 终局方案——那条路只验证「能搜到规范」，验证不了用户诉求里真正构成产品完整性的三条：素材池心智、带 diff 的策展确认、与双核会话深度绑定。SYNTHESIS 的「Phase 0 可选验证 → Phase 1 自建 MVP → Phase 2 再开策展」是我现在愿意签字的单一路径；在 BotMemory 上我坚持**写入永不互通**，只接受文案与门控范式复用，不接受 P2「收编成内置库」作为默认动作。

## D1 MVP 厚度
- 原立场：P1–P2 含素材池 + 半自动归类（可检索参考书之上，尽快露出策展差异化）。
- 看了对方后最终立场：**折中改口**——首发 MVP（Phase 1）改跟 kscc / SYNTHESIS：**库 + Markdown/纯文本直存 + FTS5 + 会话绑定 + `@kb` + candidate→active 写入门控骨架**；**素材池与半自动归类整体挪到 Phase 2**，不再与 P1 捆绑交付。不接受 mimo「策展/成稿/多格式全砍且不设回补闸门」的极瘦终局。
- 理由（≥3 句，须点名引用对方 1 条具体论点）：被 mimo「素材池 + Agent 策展是抄 Notion AI / Anthropic Projects，不是真有高频需求；MVP 做这个 = 90% 时间维护 10% 场景」说服——若把低频策展塞进首发，产品完整感会假象化，真实失败模式是面板空转与 scope 膨胀。同时接受 kscc「P1 只做手动归类 + candidate 确认，自动归类放 P2」的分期，因为它与我原 FINDINGS 里「先做可检索的项目参考书，再做有门控的策展员」一致，只是我原先把「半自动」提前得过猛。坚持保留 Phase 2 回补：若 P1 验证后用户只有直存检索、从不丢零散素材，再砍策展；若用户开始往聊天里「整理入库」，没有素材池会直接回到散乱附件堆——那是另一种「做少了」的失败。
- 对另外两方的回应：向 kscc 的 2–3 周 × 2 phase 工期感靠拢，并认同其「多视图是低频长尾、整段砍」；反驳 mimo 把「成稿/版本」与「多格式」和「素材池」捆在一起全砍——多视图我本就延后，但「直存整档」不能替代「零散待归类」心智，否则用户原始三种入库模式只剩一种，产品完整性缺口过大。

## D2 是否自建
- 原立场：自建为主，MCP 作逃生舱 / 外挂验证。
- 看了对方后最终立场：**坚持自建为主，但明确采纳 SYNTHESIS / mimo 的 Phase 0**——用「项目内 `knowledge/`（或 Obsidian 目录）+ 只读 KB 检索 MCP/AgentTool」花约 1 周验证「绑定库 + `@kb` + 来源标注」是否就是用户要的全部；**一旦验证需要策展/确认成稿/会话深度绑定，立即转入自建 `kb-store` + IPC**，不以 MCP 为终局。
- 理由（≥3 句，须点名引用对方 1 条具体论点）：kscc 反对意见写得很清楚：「若用户主要诉求是让 Agent 查得到项目文档，最低成本是本地文件夹 + 只读 KB 检索 MCP……自建 KB 的合理前提是：用户确实需要 Agent 策展入库，而不只是检索。」这条我同意，并把它升格为**立项前的失败模式分流阀**：只检索 → 自建是过度建设（R-KB6 / 「全能 RAG」失败）；要策展 → MCP 永远做不成一体化确认 UX。mimo「强烈建议先看 Obsidian + MCP，否则可能在做一个 30% 解决方案」说服我必须先对齐高频场景，但**不能把 30% 方案当成 100% 产品**：我原 FINDINGS 已写「Obsidian 文件夹 + MCP 不能替代素材池 + 确认成稿 + Agent 工具的一体化体验」。kscc「照抄 memory 范式建 `kb-store`」在确认自建之后仍然是正确工程路径，我维持。
- 对另外两方的回应：接受 mimo「先对齐要不要大建」的拍板题，拒绝其暗示的「文件夹终局」；与 kscc 一致自建落地，但要求 Phase 0 结论写入 brief v2，避免未分流就开六层 schema。

## D3 Agent 策展
- 原立场：P2 核心差异化，但必须 diff 门控；禁止无人值守改规范。
- 看了对方后最终立场：**坚持「P2 上、带 diff / candidate 确认」**；**向 mimo 让步强化 P1 纪律**——Phase 1 **零 Agent 自主写 KB**（含不自动抛合并提案）；P1 的 candidate 门控只服务「用户显式触发的整理入库 / 直存确认」，不服务后台自动策展 job。
- 理由（≥3 句，须点名引用对方 1 条具体论点）：三人其实同向：kscc「Agent 整理只产 candidate，用户确认才是唯一激活入口」、mimo「KB 阶段不该引入新的 Agent 自主写权限」、我自己「规范 Collection 强制 diff，无确认不 commit」。分歧只在「何时算核心差异化」。我仍认为 TAgent 相对 AnythingLLM「ingest→chunk→retrieve」停住的竞品，**有门控的合并成稿才是可辩护的自建理由**；若按 mimo「P1 不做、且暗示长期可不动」，自建相对 Obsidian+MCP 的产品完整性论证会塌掉。被说服的部分是：过早上半自动归类会激活失败模式 3「自动文档员工无门控 → 规范被改写后信任不可恢复」——即便有 candidate，P1 同时开检索 UX + 策展 UX 会让确认对话框沦为疲劳点击。因此差异化刻意留在 P2，且规范集合默认 append-only + 显式 diff，**首年不做无人值守**。
- 对另外两方的回应：完全同意 kscc 抄 BotMemory 门控且物理隔离 stage 队列；不同意 mimo 把策展与 L5 consolidation「行为重叠」当作永久不做的理由——重叠要用**独立入口文案 + 来源徽章**消解（R-KB1），不是用砍差异化消解。

## D4 与 BotMemory
- 原立场：严格隔离；协作室 Bot **只读**授权 Library；KB Document 永不 activate 成 BotMemory。
- 看了对方后最终立场：**坚持严格隔离（数据模型 / 写入路径 / UI 入口三分离）**；**采纳 mimo 的文案策略**（对外「项目参考书 vs Bot 经验」）；**拒绝 kscc「P2 评估收编为 KB 内置 system 库」作为默认推荐**——最多允许「门控范式 / 组件库」复用，不允许存储合并。
- 理由（≥3 句，须点名引用对方 1 条具体论点）：kscc 称 BotMemory「可视为 KB 的条目级短记忆特例，P2 评估收编」——从工程同型看有道理，但从产品失败模式看，这正是 R-KB1「心智坍缩：聊天废话、Nudge 事实、规范文档丢进同一记忆」的预埋引线。BotMemory 是 per-bot 人设/经验（candidate→active）；KB 是用户给任意 Agent 的项目档案；合并后用户分不清「改的是机器人性格还是项目规范」，协作室里一次误 activate 就会污染人设。mimo「文案上区分参考书 vs Bot 经验」不够工程，但方向对：隔离必须**用户可感知**，不能只靠 db 文件名。我维持：Bot 可 `kb.search` 房间授权库；**禁止** KB → BotMemory 写入通道；P1 并存；P2 只评估「是否抽取共享 ConfirmGate 组件」，不评估「是否收编数据」。
- 对另外两方的回应：向 mimo 让步话术与来源标签；向 kscc 让步「门控实现可抄」，不让步「域模型可并」。

## 我的终裁推荐（给用户的单一路径，5–8 行）

**写死这条路：Phase 0（可选，≤1 周）→ Phase 1 自建瘦 MVP（3–4 周）→ Phase 2 有门控策展（验证后再开，+2–3 周）。**  
- **Phase 0**：目录/Obsidian + 只读检索工具，只验证「绑定 + `@kb` + `[KB:]` 来源标注」；若这就够，停，不建子系统。  
- **Phase 1**：自建 `~/.tagent/knowledge-base/kb.db` + blobs；库 CRUD + 模板集合；MD/文本直存；FTS5；会话绑定；`@kb` dual-mount；**用户触发**的 candidate→active；KB Rail 面板；与 L0–L5 / BotMemory **写入隔离**。不做素材池、不做自动策展、不做多视图、不做默认向量引擎。  
- **Phase 2**：素材池 + Agent **提议**合并/归类（强制 diff/confirm）+ 简单 Revision 链；Office best-effort；可选 MCP 外挂重解析。  
- **明确不做（首年）**：无人值守改规范；Word/脑图/表格多视图主路径；默认 Qdrant/RAGFlow；BotMemory 收编进 KB。

## 我愿意向谁让步、不愿让步什么

- **愿向 mimo 让步**：P1 极瘦（砍素材池/半自动归类出首发）；Phase 0 先验证；对外话术「参考书」；P1 零 Agent 自主写。  
- **愿向 kscc 让步**：工期与 `kb-store` 照抄 memory 范式；candidate 门控实现；多视图与向量延后。  
- **不愿让步**：自建在「需要策展」前提下仍是主路径（MCP 非终局）；P2 有门控策展作为差异化保留；**KB ↔ BotMemory 写入永不合并**；KB 不进 L0–L2 Frozen；规范类优先仅限规范/档案集合（非全局硬编码压过一切 memory）。

## 仍需用户拍板的问题（≤3）

1. **高频场景分流**：只要「规范能被搜到」，还是明确要「素材池 + 确认后成稿」？（决定 Phase 0 停还是进自建 Phase 1）  
2. **Library 作用域**：per-workspace 还是全局？会话可否绑多库？  
3. **规范集合写入**：永远人工 confirm，还是允许「信任模式」仅自动 append（仍禁止静默改写/合并）？
