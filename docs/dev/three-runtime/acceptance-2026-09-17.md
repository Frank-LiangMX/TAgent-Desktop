# 三内核实机验收 — 2026-09-17

## 结论

**部分通过，暂不判为可发布。** 真账号的短对话接续、宿主历史保留、Pi 只读工具及一次停止切换跑通；发现 Codex 成功终态映射缺陷。交接异常恢复、完整 UI 端到端和长上下文边界仍未通过验收。本轮只做验收，没有修改产品实现。

## 方法与隔离

- 启动现有构建 `apps/electron/dist/main.cjs`，界面使用该构建的 Vite preview。
- `live-acceptance.cjs` 捕获真实 IPC 注册并调用实际 handler，实际运行原有适配器，不替换为 mock。流式输出、原生 ID 与落盘记录用于核对，而非只问模型“你是谁”。
- 独立临时配置和工作目录，不复制正式聊天。仅复制渠道配置和本机 Chromium 加密状态以便同机解密；未输出凭据，不更改正式渠道。KSCC 只在验收副本启用。
- Codex 使用配置模型 `gpt-5.6-luna`；KSCC 使用本机 `deepseek-v4.1-flash`；Pi 分别测试配置中的 `deepseek-v4-flash` 和 `grok-4.6`。
- 会话 `acceptance-runtime-20260917`；虚构代号 `ORBIT-731`，约束“不得修改任何文件”。只读工具读取验收夹具 `fixture-value: COBALT-842`。不让 Agent 修改项目。
- 强制结束自己创建的验收进程后重新启动，验证绑定与待投递记录的恢复；不是仅重载页面。

## 实测结果

| 场景 | 结果与证据 |
| --- | --- |
| Pi 首次调用 DeepSeek | 最初因隔离 profile 没有原加密状态，密钥解密失败；这是验收环境问题，随后补齐 |
| Pi 不可用时切到 Codex | 成功，不依赖 Pi 生成总结；聊天记录不变 |
| Codex 接续 | 约 27 秒，正确回答 `ORBIT-731；不修改文件`；真实 `codexThreadId` 已保存；但成功交接被误标 ambiguous，见缺陷 1 |
| Codex → KSCC | 成功，历史不变，旧原生 ID 清空后新建；约 8 秒正确回答代号和约束，交接被消费 |
| KSCC → Pi，待投递时退出重开 | 绑定、revision=3、待投递交接均保留；Pi/DeepSeek 实际请求得到 HTTP 500 无正文，未伪报成功 |
| Pi 换到配置中的 Grok | 约 6 秒正确续聊，说明该路径可调用真实模型；此前 ambiguous 记录仍残留，见缺陷 2 |
| 无效目标模型 | 明确拒绝，切换前后绑定完全相同 |
| Pi / Grok 只读工具 | 读取独立临时文件，回答 `COBALT-842`，约 6 秒 |
| 回合正在执行时切核 | 拒绝，提示先停止；随后停止 ACK 返回，等待回合结束后可以切换 |
| 再切回 Pi 后退出重开 | revision=6 和 pending 记录恢复；Grok 约 6 秒正确回答代号和约束，成功后 pending 清除；可见记录共 20 条 |

这里的停止用例发生在短请求刚启动时，不证明长时间运行的写工具、审批在途和掉队子进程全部安全。测试 harness 的 `ended=true` 只表示观察到终态，不等于业务成功；业务结果须结合 `subtype/errors/output`。

## 发现的问题

### 1. P1：Codex 正常完成被判为交接失败/未知

真实输出 `{ kind: 'result', subtype: 'completed' }`，模型已正确回答，但 `runtimeHandoff.lastOutcome` 变成 `ambiguous`。

- `codex-event-normalizer.ts` 的 `turnCompleted` 原样把原生 `status` 写为 subtype。
- `session-runtime.ts` 的 `classifyTurnTerminal` 只接受 `subtype==='success'`，把 `completed` 判为 error。
- 现有适配器测试本来就断言 `completed`，而新增 IPC 测试用的是 `success`，因此各自通过却在拼接时出错。

修复方向：统一终态契约，明确成功、取消、失败，不简单把所有 result 当成功；增加真实 normalizer → runtime → handoff 的跨层测试。

### 2. P1：交接结果不明缺少恢复闭环

Pi 请求 500 后 attempts=1/outcome=ambiguous 被持久化。随后换同一 Pi 内核的 Grok 模型，已能正确回答，但该状态仍保留。`shouldInjectHandoff` 对 attempts>0 不再注入，也没有 UI 解释或显式重新准备交接入口。

本次短历史能通过另一路面板恢复接上，不能据此认定长会话也可靠。应区分“没有送达”“可能已送达”“新建原生上下文后需要补入”，避免自动重放原任务；提供明确恢复入口。再次跨核生成全新 pending 后，本次重开测试可正常消费。

### 3. P2：Pi 记忆 FTS 查询走降级

实际日志出现 `SqliteError: no such column: fts`；`memory-layer-service.ts` 查询使用 `WHERE fts MATCH ?` / `bm25(fts)`。本次 fallback 后仍能回答，不是全功能失效，但主搜索路径未正常工作，应独立修复验证。

### 4. 外部调用失败尚未归因

Pi + 当前网关的 DeepSeek 返回 HTTP 500 无正文；同渠道 Grok 正常。不足以断言是上游算力、模型别名还是请求兼容性，应另做脱敏请求级定位，不能算 Pi 所有模型已验收。

## UI 与未覆盖项

依据 computer-use 技能检查了实际验收窗口和持久化会话列表；未触碰正式 TAgent 窗口。隔离配置无工作区，界面停在工作区欢迎页。目录选择框出现 UI Automation 索引/焦点异常，因此停止进一步输入，**没有完成通过 Agent 下拉菜单发送的全 UI 验收**。IPC/真实内核结果不得替代这一项。

未覆盖：长对话中段约束、图片和附件迁移、写工具停止、审批与权限跨核一致性、所有两两切换组合、标准 Claude Code、模型质量与长期稳定性。未生成安装包。

## “不是完整上下文迁移”的准确含义

宿主聊天记录还在，但交给新内核的不是旧内核的完整记忆。首版给出初始目标、最近要求、宿主模式/权限、路径线索和最近优先约 12,000 字符的可见历史，总预算约 14,000 字符；不转移隐藏思考、运行中工具和原生状态，旧原生 ID 仅归档。

因此短会话通常能接上；长任务较早和中段的关键限制可能未带入，图片路径也不等于看过图片。这些是当前实现边界，不是多内核方案必须永久接受的限制。后续应保留结构化约束/任务状态、按目标容量分配预算，并为省略历史提供可查询入口；即便如此也不应承诺迁移不可访问的原生隐藏状态。
